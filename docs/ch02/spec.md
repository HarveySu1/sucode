# sucode · Phase 2 规格 —— 工具系统与 Agent 循环

> 状态：已与需求方澄清定稿（2026-10-17）
> 本文档只回答「做什么、不做什么、什么算完成」。实现细节见同目录 tasks.md，验收值见同目录 checklist.md。

## 1. 背景

Phase 1 完成了可靠的对话内核（流式、thinking、多 profile、中断）。Phase 2 给 sucode 装上工具系统：模型识别自己要用哪个工具，sucode 去执行，再把结果喂回去，模型据此作答——从聊天机器人变成能干活的 Agent。

本期先落地**单步** Agent（一次工具执行轮 + 一次最终回复轮），随后在**同一章内修订**为**真正的 Agent 循环**：模型可连续多轮调用工具，直到自认信息足够再产出最终回复；并补齐长任务**可见性**——Bash 执行期间增量输出、所有工具执行期间展示心跳计时。单步版原本让「先列目录 → 再读文件 → 再改文件」这类多步任务无法在一次提问内完成，用户被迫反复追问；Bash 也「跑完才返回、无增量输出、无进度」，长命令看起来像卡死。

## 2. 能力清单（续 Phase 1 编号）

- C16. 统一 Tool 接口：每个工具实现统一抽象（名称 / 描述 / 参数 Schema / 分类元信息 / 异步执行方法）
  - 对齐修订：分类元信息由 `read_only` 布尔改为 `category`（C35）；参数 Schema 由手写改为 Pydantic 自动生成（C34）
- C17. 六核心工具：ReadFile、WriteFile、EditFile、Bash、Glob、Grep，覆盖读/写/改/执行/找文件/搜内容
- C18. 注册中心：集中登记工具、按名查找、转换为双协议各自认得的工具列表格式
- C19. 工具执行保护：带超时；未知工具 / 禁用工具 / 参数 JSON 解析失败 / 参数校验失败 / 执行异常 / 超时，全部包成结构化失败结果（`is_error=true` + 错误文案）回传模型，由模型自行调整，程序不崩溃
- C20. 流式工具调用解析：双协议（Anthropic tool_use / OpenAI tool_calls）流式聚合，JSON 参数碎片拼接完整；参数为空串时归一为空对象
- C21. tool_result 回传：执行结果回灌对话历史，模型据此产出最终回复；本轮内最多一次工具执行轮
- C22. EditFile 语义：原文唯一匹配替换；匹配 0 次或多次均给出可指引模型重试的明确报错
- C23. TUI 工具过程展示：单轮单块——思考（暗淡）→ 工具行（名称 + 参数流式，执行后带 ✓/✗ 状态与摘要）→ 最终 Markdown 正文，同属一个 AI 消息块
- C24. 配对不变量：任何路径下（中断 / 出错 / 正常），入史的 tool_use 必有紧邻配对的 tool_result（Anthropic 硬约束）；中断边界规则如下
  - 一轮流中被中断：半截正文照 Phase 1 规则入史，未完成的 tool_calls 整体丢弃（防孤儿）
  - 工具执行中被中断：当前及剩余工具全部配对「用户中断」结果（`is_error=true`）后入史，轮次收尾
  - 二轮流中被中断：有半截入史标中断；一字未出则回滚整轮（弹掉 assistant(tool_calls) 与 user(tool_results)），回到用户消息结尾
  - 工具失败 / 超时：以 is_error 结构化结果回传，**继续**二轮流让模型调整
- C25. thinking 与工具的协议兼容：
  - Anthropic：带 tool_use 的 assistant 回传时 thinking + signature 必须原样回传（仅最后一工具轮，更早轮次剥离省 token）；signature 由流内 signature_delta 捕获
  - OpenAI 兼容端：带工具时 assistant 的 reasoning_content 必须回传（DeepSeek 硬性要求，否则 400）
  - 留存范围：thinking / signature 仅在**带工具的会话**入史（含无 tool_calls 的收尾轮）；纯对话路径（无注册中心）一律不入史，避免无谓占用历史 token
- C26. 二轮回复又请求工具调用：不执行，剥离 tool_calls 后入史，界面提示「连环调用属下一章能力」
  - 本节修订（单步 → 循环）后：C26 被 C27 取代，模型再次请求工具时**执行**而非提示

### 修订部分（单步 → Agent 循环 + 工具执行反馈）

- C27. Agent 循环编排：一轮工具执行完成后自动继续下一轮，直到模型不再请求工具（产出最终回复）；替代 C26 的「二轮不执行」限制
- C28. 循环安全上限与收尾：设最大工具轮数（10）；达到上限后不再向模型提供 / 执行工具，改为强制其基于已有结果产出最终回复，并提示用户已达上限
- C29. 配对不变量在循环中延续：任意轮次的 assistant(tool_calls) 与同轮 user(tool_results) 紧邻配对；中断 / 出错边界规则覆盖任意轮次（延续 C24）
- C30. Bash 流式输出：Bash 执行期间增量产出 stdout/stderr 片段并实时回传界面（其余工具不做增量输出）
- C31. 工具执行心跳与耗时显示：任意工具执行期间周期性产出「运行中 + 已用秒数」反馈；工具行始终展示已用秒数（保留一位小数），运行中逐次刷新、执行结束后展示总耗时，用于提示工具是否卡死
- C32. 多轮过程呈现：每个 LLM 轮次独立成一个 AI 消息块（思考 → 工具行 → 正文）；工具行展示流式输出片段与心跳状态，执行后带 ✓/✗ 与摘要（取代 C23 的「单轮单块」）
- C33. 逐轮确定性清理：每轮流仍各自创建、各自关闭，不因循环变长而泄漏

### 对齐部分（图片3 设计表：设计决策 → Python 实现）

- C34. 参数校验：每个工具声明 Pydantic 参数模型，JSON Schema 由 `model_json_schema()` 自动生成；入参经模型校验，缺失 / 类型不符 → 可读报错回传模型
- C35. 工具分类：`category` 为 `Literal["read", "write", "command"]`，静态类型检查；读类 ReadFile/Glob/Grep、写类 WriteFile/EditFile、命令类 Bash
- C36. 结果传递：`ToolResult` dataclass（`output` + `is_error`），失败以结构化结果回传让模型自行处理
- C37. 注册机制：`ToolRegistry` 用 dict 存储，支持 `disable` / `enable` 动态管理——被禁用的工具既不暴露给模型也不可执行
- C38. 文件缓存：`FileCache` 线程安全字典（以「路径 + mtime」为键），ReadFile 读时填充，EditFile / WriteFile 写后失效
- C39. 异步执行：所有 `execute` 均为 async；Bash 用 `asyncio.create_subprocess_shell` 拉起子进程
- C40. 延迟加载：`should_defer` 类属性 + 评分搜索（提问与工具名/描述的词面重合打分，按 top_k 择优暴露）；本期六工具均不延迟，仅机制就绪
- C41. 协议适配：`get_all_schemas(protocol)` 按参数区分 Anthropic / OpenAI 的工具列表格式

## 3. 非功能要求

- N6. 输出截断防失控：单工具结果 30000 字符（超出保留头尾各半并注明）；ReadFile 默认 2000 行；Glob 上限 500 条；Grep 上限 200 处命中
- N7. 依赖：新增 Pydantic 作为工具参数校验与 Schema 自动生成（取代手写 Schema）；搜索仍用纯 `re` 实现，不引入 ripgrep
- N8. 序列化协议合规：Anthropic 空正文省略 text 块（严禁空 text 400）；tool_result 块排在 user 正文之前；空参数归一空对象；内部历史保持 user/assistant 严格交替（tool_results 挂 user 消息，仅序列化时按协议展开）
- N9. Bash 为 Windows PowerShell 一等公民：`-NoProfile -NonInteractive` + `chcp 65001` + UTF-8 解码，退出码显式传递（`exit $LASTEXITCODE`），超时 / 取消杀整棵进程树

### 修订部分（Agent 循环 + 工具执行反馈）

- N10. 循环保护：工具轮数存在硬上限，杜绝模型持续调工具导致的死循环与 token 失控
- N11. Bash 流式读取不阻塞：增量读取与整轮超时 / 取消共存；超时或取消仍杀整棵进程树
- N12. 心跳节流：心跳按固定间隔（2s）产出，避免高频刷屏与事件风暴
- N13. 工具接口最小侵入：不强制所有工具改造即可获得心跳；仅 Bash 覆写流式路径
- N14. 双协议兼容延续：Anthropic thinking/signature 仅在最后工具轮回传、OpenAI 带工具回传 reasoning_content 的规则在任意轮次仍成立

### 对齐部分（图片3 设计表）

- N15. PowerShell 错误流净化：自身错误流被包装成 CLIXML（实际首行是 `#< CLIXML` 后跟换行、末尾无 `>`），必须剥掉 XML 噪音同时保留其中错误正文——CLIXML 形态因协议细节失配而剥不干净时，模型将同时收到噪音与缺失线索

## 4. 设计骨架（在 Phase 1 骨架上新增工具层）

```
┌────────────────────────────────────────────────┐
│ TUI 层：+ 工具行渲染（ToolCallStart/Delta/执行状态）│
├────────────────────────────────────────────────┤
│ 会话层：+ 单步工具编排（聚合→执行→回传→二轮）        │
├───────────────────────┬────────────────────────┤
│ Provider 层            │ 工具层（新增）             │
│  + 流式 tool 解析        │  Tool 抽象 + 六工具实现    │
│  + serialize 双协议分叉 │  ToolRegistry 注册中心    │
├───────────────────────┴────────────────────────┤
│ 配置层（不变）                                     │
└────────────────────────────────────────────────┘
```

依赖方向沿用 Phase 1：会话层依赖工具层与 Provider 层；工具层独立无依赖；TUI 只消费事件。

修订后骨架（单步 → 循环，新增工具执行反馈通道）：

```
┌──────────────────────────────────────────────────┐
│ TUI 层：+ 每轮新块 + 工具行流式输出 / 心跳渲染        │
├──────────────────────────────────────────────────┤
│ 会话层：+ Agent 循环（执行→回传→再请求…直到收尾）      │
│         + 工具执行反馈编排（心跳计时 / 输出分片排空）   │
├───────────────────────┬──────────────────────────┤
│ Provider 层            │ 工具层                     │
│  + 轮次开始 / 反馈事件   │  + 可选流式执行入口（默认退化）│
│                        │  + Bash 覆写为增量流式        │
├───────────────────────┴──────────────────────────┤
│ 配置层（不变）                                       │
└──────────────────────────────────────────────────┘
```

## 5. 已知限制（接受，不预防）

- L1. 工具轮结束后 `/profile` 热切换到 thinking 配置不同的模型，可能因签名校验 400——错误处理兜底为可读提示（可用 `/new` 重开）
- L2. 二轮流一字未出的中断 / 错误走整轮回滚，已执行工具的副作用（如已写入的文件）不撤销
- L3. 循环中的工具失败仍以结构化结果回传让模型自愈，但模型可能反复重试同一失败工具直到触及轮数上限
- L4. 多轮已执行工具的多步副作用（如多轮写入文件）在中途中断时不回滚
- L5. Bash 增量输出只用于「看到进度」，不做交互式 stdin，仍不支持需要输入的交互命令

## 6. Out of Scope（本期明确不做）

- O11. 权限确认流程（仅 `category` 分类元信息，确认 UI 属后续能力）
- O12. 并发执行（多工具一律串行）
- O13. system prompt（本期不加，靠工具 description 传递上下文）
- O14. 工具级重试策略、用量统计、工具执行的差异回显
- O15. Bash 交互式 stdin / 伪终端（保留 L5）

## 7. 完成定义

Phase 2 完成当且仅当：checklist.md 全部条目实际操作通过，含两条硬性要求：mock 回归全绿（含 Phase 1 原有用例不回归破坏）；真实 API 下模型主动发起工具调用并完成「创建文件 / 搜索代码」任务各一次。

修订部分（Agent 循环 + 工具执行反馈）追加硬性要求：真实 API 下模型在一次提问内主动完成「≥2 轮串行工具调用」的多步任务，且长耗 Bash 命令执行期间界面可见增量输出与心跳计时。

对齐部分（图片3 设计表）追加硬性要求：工具参数 Schema 由 Pydantic 生成且两种协议格式各自正确；参数校验失败 / 禁用工具 / 未知工具均返回结构化失败结果而不崩溃；文件缓存读时填充、写后失效（不吃陈旧内容）；Bash 在 `create_subprocess_shell` 下仍保持中文无乱码、退出码正确、超时杀树、CLIXML 剥净且错误正文保留。
